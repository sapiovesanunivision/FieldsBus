## D5 scope

Done when: **a signed driver installs on a clean Windows 11 PC with Secure Boot on, through an installer, next to an
installed Npcap, and the PROFINET device reaches DataRun against CODESYS.** Three work streams, plus docs.

### A. Signing route (management decision first)

Facts from 2026-10-16, re-check them all **[verify]**, because Microsoft's policy was changing:
- Windows 10/11 load only Microsoft-signed kernel drivers. Every route needs a company **EV code-signing
  certificate** and a **Microsoft Partner Center (hardware dashboard)** account.
- **Attestation signing** is now titled "for testing scenarios": not Windows Certified, not on Windows Update.
- Since the April 2026 update, Windows 11 24H2/25H2/26H1 and Server 2025 trust by default only drivers "properly
  signed through WHCP" plus an allow-list (audit-only phase first). Whether attestation-signed drivers still load
  there is **not stated**.
- Windows Server 2016+: only HLK-passed (WHCP) drivers.
- Likely product path: **WHCP with HLK tests**. Open: which HLK test set applies to an NDIS *protocol* driver
  (NetTrans, no hardware ID), and what static-analysis results (CodeQL / "Static Tools Logo") the submission needs
  **[verify]**.
- Enterprise-only alternative: an App Control for Business (WDAC) policy signed with the machine's keys. Not
  practical for customer stations.

What to do:
1. Write a short decision note for the user / management. It should cover:
   - the routes;
   - cost: EV certificate per year, HLK effort (an HLK controller plus a test client);
   - lead time: company validation for the EV certificate takes weeks;
   - risk: will attestation still load on 24H2+?
   - the comparison the project started with: Npcap OEM licence about $80k, a Hilscher card about 200 EUR per
     station.

   **The user decides. Do not buy, register or submit anything.**
2. Things that do not need the decision, and can start now:
   - **Release build** in `build.ps1` / `pack_kit.ps1`; install the Spectre-mitigated libs with the user's OK.
   - Version: `DriverVer` and `softpn_ndis.rc` from one place, bumped per release; `GET_VERSION` stays the API
     version.
   - InfVerif in the mode the submission requires (**[verify]**: `/w` or `/h`) and a clean CodeQL / SDV run.
   - Production `FrameTypeArray`: drop 0x88B5 (test-only EtherType)? It is also what `pn_probe` and the selftest
     use. Decide with the user.
3. As soon as an attestation- or WHCP-signed build exists: test it on a 24H2/25H2 PC with Secure Boot **on**.

### B. Installer

Today there is no installer in the repo (no WiX/MSI/MSIX), only the test scripts. Points to settle:
- **How protocol drivers get installed:** SetupAPI / `pnputil` cannot install a NetTrans protocol (no hardware
  ID). Both `netcfg.exe` and an installer use the **INetCfg COM API** (`INetCfgClassSetup::Install` with
  `OBO_USER`), after the package is staged with `SetupCopyOEMInf` / `pnputil /add-driver` **[verify]**. Microsoft's
  `bindview` / netcfg samples show INetCfg usage **[verify path]**.
  - Proposal: a small `softpn_ndis_setup.exe install|uninstall|status`, statically linked, that the product
    installer calls. Or call `netcfg.exe` from the installer, if that is acceptable.
- **Which installer:** ask the user what the product (ProInspect / the Dev.3 PROFINET service) is shipped with.
  Dev.3 PROFINET integration (Phase 9.19) is **on hold**: do not touch `D:\Univision\Dev.3`.
- **Start type:**
  - Now it is demand start, and the tests used `net start SoftPnNdis`.
  - The backend opens `\\.\SoftPnNdis`, so the driver must run before the PROFINET service starts. Options:
    - `StartType=2` (auto);
    - NDIS loading the protocol at bind time **[verify whether NDIS starts a demand-start protocol by itself]**;
    - the service starting it.
  - Test after a cold boot.
- **Bindings:** it binds to every adapter, including Wi-Fi, Hyper-V vEthernet and VPN. Should the installer unbind
  all but the PROFINET NIC (`Disable-NetAdapterBinding -ComponentID UV_SoftPnNdis`, or INetCfg)? Or should the
  INF be narrowed? A binding costs little (two allocations, no traffic unless opened), but less is cleaner.
- **Upgrade and uninstall:**
  - Upgrade = uninstall + install interrupts PROFINET: the service must be stopped first. The backend now
    reopens after an unbind (`NdisPort::reopen()`), so a running device recovers if the driver comes back.
  - Uninstall must remove the driver-store package (`pnputil /delete-driver oemNN.inf`) **[verify]**.
  - No reboot was needed in any test so far.
- No test certificate on customer PCs: `install.cmd`'s certutil and testsigning steps are test-only.

### C. Coexistence with Npcap

Npcap is an NDIS **filter** driver (LWF, in every binding stack); ours is a **protocol** driver. Packet filters of
all bindings are ORed by NDIS. Nothing has been tested with both installed and active on the same NIC yet.

Test matrix (on the physical test PC, CODESYS at 8 ms, 20-30 min each, note `max TX period`, `late`, `aborts`):

| # | Setup | What to check |
|---|---|---|
| C1 | Npcap installed, not in use, our driver in use (`--backend ndis`) | same timing as without Npcap |
| C2 | as C1 + Wireshark capturing on the same NIC, promiscuous **off** | no aborts; Wireshark sees the PROFINET frames |
| C3 | as C2, promiscuous **on** | no aborts; no duplicate or own frames in the device (`softpn_ndis_test` counters: `dropped own`) |
| C4 | `--backend auto` with both present | picks `ndis` (`pn_probe --list` shows `[ndis]`) |
| C5 | Npcap uninstalled / reinstalled while our driver is installed (and the reverse) | both keep working, no reboot surprise |
| C6 | `--backend npcap` app on the same NIC at the same time as an `ndis` app | expected to work (different stacks); document what happens |

Known from earlier: a Wireshark capture in promiscuous mode makes the NIC promiscuous for everyone; this hid a
test result once.
